### ⚠️ QM-01 — HIGH: "ชื่อชุมชน" บนกระดาษเป็นช่องเขียนอิสระ แต่ไม่มีฟิลด์เก็บ

**ปัญหาคืออะไร:** กระดาษให้ผู้สำรวจ**เขียนชื่อชุมชนด้วยมือ** (`ชื่อ ชุมชน: ..................`) ไม่ใช่ checkbox แต่ Schema กำหนด `Household.communityId` เป็น FK บังคับ (`String` — NOT NULL, schema.prisma:713) ซึ่งได้ค่ามาจาก Batch แทน

**พบในไฟล์ใด:** `questionnaire.pdf` หน้า 1 ส่วนที่ 0 vs `prisma/schema.prisma:713`

**ผลกระทบ:**
1. **ข้อมูลบนกระดาษหาย** — ถ้าผู้สำรวจเขียน "ชุมชนท่าเคียน" แต่ใบนั้นอยู่ใน Batch ของ "ชุมชนประสานมิตร" (ปึกปนกัน) ระบบจะบันทึกชุมชนผิดโดยไม่มีร่องรอย และตรวจสอบย้อนหลังไม่ได้เลย
2. ผู้สำรวจอาจเขียนชื่อไม่ตรงกับชื่อทางการ (เช่น "ท่าเคียน" vs "ชุมชนท่าเคียน" vs สะกดผิด) → ต้องมีขั้นตอน Mapping
3. ผิดหลัก "📋 ค่ามาจากกระดาษ (ห้าม default = ค่าปัจจุบัน)" ที่ Schema เองประกาศไว้ (schema.prisma:11)

**แนวทางแก้ไข:** เพิ่ม `Household.communityNameOnPaper String?` (📋 ค่าดิบจากกระดาษ) + คง `communityId` เป็นค่าที่ Map แล้ว + เพิ่ม Validation เตือนเมื่อ `communityNameOnPaper` ไม่ตรงกับ `community.nameTh` ของ Batch → ให้ Verifier ตัดสิน (ดู FIX-10)

**ต้องใช้ข้อมูลเพิ่มเติม:** 1 Batch = 1 ชุมชนเสมอหรือไม่? (schema.prisma:522 บอก "1 ปึก = 1 ชุมชน **โดยปกติ**" — คำว่า "โดยปกติ" แปลว่ามีข้อยกเว้น) (ดู Q-09)

**Module ที่กระทบ:** M02, M03, M04

### ⚠️ QM-02 — MEDIUM: วันที่สำรวจ — พ.ศ. หรือ ค.ศ.?

**ปัญหา:** กระดาษเขียน "วันที่ / เดือน / ปี" โดยไม่ระบุว่าเป็น พ.ศ. หรือ ค.ศ. → ผู้สำรวจไทยจะเขียน **พ.ศ.** (เช่น 68 หรือ 2568) แต่ `DateTime` ใน DB เป็น ค.ศ.

**ผลกระทบ:** ถ้าคีย์ "2568" ตรงๆ → วันที่ผิดไป 543 ปี → กระทบ **ทุกการคำนวณที่อิง `surveyedAt`**: อายุครรภ์ (FR-VUL-08), Triage staleness (BR-48/57), `STALE_DATA_MONTHS` (seed.ts:339), และ RK-E14 (ข้อมูลล้าสมัย)

**หลักฐานว่าระบบคาดหวัง พ.ศ.:** `FloodRiskProfile.lastFloodYear` มี Comment ว่า "ปี **พ.ศ.** ที่ท่วมล่าสุด" (schema.prisma:956) → แสดงว่าระบบปนกัน (บางฟิลด์ พ.ศ. บางฟิลด์ ค.ศ.)

**แนวทางแก้ไข:** กำหนดกฎแปลงที่ Entry Console (รับ พ.ศ. → แปลงเป็น ค.ศ. ก่อนบันทึก) + แสดงผลกลับเป็น พ.ศ. + เขียน Unit Test + **ห้ามเก็บ พ.ศ. ลง DateTime** และสำหรับ `lastFloodYear Int?` ต้องระบุหน่วยให้ชัดใน Zod Schema (ดู Q-10)

**Module ที่กระทบ:** M03, M08, M09

### ⚠️ QM-03 — BLOCKER: `@@unique([houseNo, mooId, tambonId])` ใช้กันข้อมูลซ้ำไม่ได้จริง และบล็อกอพาร์ทเมนต์

**ปัญหาคืออะไร (2 ประเด็นในข้อจำกัดเดียว):**

**(ก) กันซ้ำไม่ได้จริง** — ทั้ง 3 คอลัมน์เป็น Nullable ใน PostgreSQL ค่า `NULL` **ไม่ถือว่าเท่ากัน** (`NULL != NULL`) ดังนั้น:
- ใบที่ `houseNo` อ่านไม่ออก (ILLEGIBLE → NULL) จะ Insert ซ้ำได้ไม่จำกัด โดย Constraint ไม่ฟ้องเลย
- ซึ่งเป็นกรณีที่**เกิดบ่อยที่สุด** (PE4 ลายมืออ่านไม่ออก เป็นปัญหาระดับ 🟠 สูง)

**(ข) บล็อกข้อมูลที่ถูกต้อง** — กระดาษข้อ 1 มีตัวเลือก **"อพาร์ทเมนต์ / แมนชั่น / ห้องเช่า"** ซึ่งโดยธรรมชาติมี**หลายครัวเรือนที่บ้านเลขที่เดียวกัน** (เช่น 99/1 ห้อง 101, 102, 103 — แต่กระดาษไม่มีช่อง "เลขห้อง") → ใบที่ 2 ของอพาร์ทเมนต์เดียวกันจะ **Insert ไม่ได้** → ผู้คีย์ติดตายกลางงาน

**พบในไฟล์ใด:** `prisma/schema.prisma:813`, `questionnaire.pdf` หน้า 1 ข้อ 1 และข้อ 3

**ผลกระทบเพิ่มเติม:** `Household` มี Soft Delete (`deletedAt`, schema.prisma:782) แต่ Unique Constraint **ไม่รู้จัก Soft Delete** → เมื่อลบใบซ้ำแบบ Soft แล้วคีย์ใหม่ที่อยู่เดิม จะชนกับแถวที่ "ลบไปแล้ว" → ผิด BR-29 โดยปริยาย

**แนวทางแก้ไข:**
1. **ลบ** `@@unique([houseNo, mooId, tambonId])` ออกจาก DB Constraint
2. เปลี่ยนการตรวจซ้ำเป็น **Soft Check ที่ Application** (FR-ENT-16) → เตือนผู้คีย์ว่า "พบใบที่อยู่ซ้ำ" แล้วให้ตัดสินใจ (ใช้ `hasDuplicateFlag` ที่มีอยู่แล้ว + M07 Duplicate Merge)
3. หากต้องการ Constraint จริง ให้ใช้ **Partial Unique Index** ที่ยกเว้น NULL และ Soft-deleted:
   `CREATE UNIQUE INDEX ... ON household(houseNo, mooId, tambonId) WHERE deletedAt IS NULL AND houseNo IS NOT NULL AND mooId IS NOT NULL AND tambonId IS NOT NULL AND buildingTypeId != <APARTMENT>` — แต่**ไม่แนะนำ** เพราะยังบล็อกอพาร์ทเมนต์อยู่ดี

**ข้อเสนอที่แนะนำ:** ใช้ข้อ 1+2 (ตรวจที่ App + Merge Flow) เพราะกระดาษไม่มีข้อมูลพอจะระบุ Uniqueness ได้จริง

**ต้องใช้ข้อมูลเพิ่มเติม:** กรณีอพาร์ทเมนต์ ผู้สำรวจกรอก 1 ใบต่อ 1 ห้อง หรือ 1 ใบต่อ 1 อาคาร? (ดู Q-12)

### ⚠️ QM-04 — HIGH: พิกัด GPS บนกระดาษเป็น "ช่องข้อความเดียว" แต่ Schema แยก 2 คอลัมน์ตัวเลข

**ปัญหาคืออะไร:** กระดาษมีช่องเดียว — `พิกัด GPS / ละติจูด-ลองจิจูด: .........................................`
พร้อมคำแนะนำ *"หากใช้สมาร์ตโฟน สามารถปักหมุดผ่าน Google Maps แล้วนำค่าพิกัดมาใส่ในช่องนี้"*

แต่ Schema แยกเป็น `latitude Decimal(10,7)?` + `longitude Decimal(10,7)?` (schema.prisma:744-745)

**ผลกระทบ:** ผู้สำรวจจะเขียนได้หลายรูปแบบมาก เช่น:
- `7.0086, 100.4747` (ทศนิยม คั่นด้วย comma)
- `7.0086 100.4747` (คั่นด้วยเว้นวรรค)
- `7°00'31"N 100°28'29"E` (DMS)
- `https://maps.app.goo.gl/xxxx` (แปะลิงก์ — คำแนะนำบนกระดาษชวนให้ทำแบบนี้!)
- `N7.0086 E100.4747`
- เขียนกลับด้าน (lng ก่อน lat)

ผู้คีย์ต้อง**ตีความและแปลง** ก่อนกรอกลง 2 ช่อง → ขัดกับ PE6 ("เจ้าหน้าที่คีย์ตีความต่างกัน") และ **ทำให้ Double-entry ไร้ความหมาย** เพราะ Entry 1 กับ Entry 2 อาจตีความต่างกันทั้งที่อ่านค่าเดียวกัน → เกิด Discrepancy เท็จ

ที่สำคัญ: **ค่าดิบที่เขียนบนกระดาษหายไปถาวร** — ตรวจสอบย้อนหลังไม่ได้ว่าคีย์ผิดหรือกระดาษผิด (ขัดกับ RK-E13 "พิกัดผิด" ที่ต้องมี Coordinate Validation Pipeline)

**แนวทางแก้ไข:**
1. เพิ่ม `Household.coordinateRawText String?` — เก็บสิ่งที่เขียนบนกระดาษ **ตามตัวอักษร** (📋)
2. ให้ `latitude`/`longitude` เป็น **ค่าที่ Parse แล้ว** (Derived)
3. **Double-entry ต้องเทียบที่ `coordinateRawText`** ไม่ใช่ที่ lat/lng ที่ผ่านการตีความ
4. เขียน Parser เป็น **Pure Function + Unit Test** รองรับรูปแบบข้างต้น + คืนค่า `ParseResult { ok, lat, lng, format, confidence }`
5. ถ้า Parse ไม่ได้ → `FieldStatus = ILLEGIBLE` + เข้า Field Query Loop (BP-04)

**Module ที่กระทบ:** M03, M04, M10

### ⚠️ QM-06 — HIGH: อายุครรภ์ — กระดาษไม่ระบุหน่วย แต่ Schema บังคับเป็น "สัปดาห์" + CHECK 1–42

**ปัญหาคืออะไร:**

| แหล่ง | ข้อความ |
|---|---|
| `questionnaire.pdf` หน้า 2 | "หญิงตั้งครรภ์ (ระบุ **อายุครรภ์**)" — **ไม่ระบุหน่วย** |

| `prisma/schema.prisma:908` | `pregnancyWeeks Int?` — บังคับเป็นสัปดาห์ |
| `00_postgis_extensions.sql:280-282` | `CHECK (pregnancyWeeks >= 1 AND pregnancyWeeks <= 42)` |

**ผลกระทบ:** คนไทยส่วนใหญ่บอกอายุครรภ์เป็น **"เดือน"** ("ท้อง 7 เดือน") ไม่ใช่สัปดาห์ เมื่อผู้สำรวจเขียน "7 เดือน" หรือแค่ "7":
- ถ้าผู้คีย์กรอก `7` ตรงๆ → ระบบตีความเป็น 7 **สัปดาห์** (≈ 1.6 เดือน) → **Triage ผิดอย่างร้ายแรง** เพราะ Seed comment บอก "≥32 สัปดาห์ จะยกเป็น P1" → หญิงตั้งครรภ์ 7 เดือน (≈30 สัปดาห์) ที่ควรใกล้ P1 จะถูกจัดเป็น P2 ที่คะแนนต่ำ
- ถ้าผู้คีย์**แปลงเอง** (7 เดือน → 30 สัปดาห์) → ขัด PE6 (ตีความต่างกัน) และ BR-54 (ห้ามคนคีย์ประเมินเอง)
- CHECK 1–42 จะ **Reject** ถ้าเขียน "40 สัปดาห์+" หรือหน่วยปนกัน

**แนวทางแก้ไข:**
1. เพิ่ม `PersonVulnerability.pregnancyRawText String?` (📋 ค่าดิบตามกระดาษ) + `pregnancyUnit` enum (`WEEKS` / `MONTHS` / `UNKNOWN`) + `pregnancyValue Int?`
2. คำนวณ `pregnancyWeeks` เป็น **Derived Field** จาก raw + unit (Pure Function + Unit Test)
3. ถ้า `unit = UNKNOWN` → ห้ามเดา → `FieldStatus = ILLEGIBLE` → Field Query Loop
4. ผ่อน CHECK เป็น 1–45 หรือย้ายไป Application Validation
5. **แก้กระดาษรอบหน้า** ให้ระบุหน่วยชัดเจน: "ระบุอายุครรภ์ ______ สัปดาห์ (หรือ ______ เดือน)"

**ต้องใช้ข้อมูลเพิ่มเติม:** ยืนยันกับผู้สำรวจว่าบรีฟให้เขียนหน่วยอะไร (ดู Q-14)

### ⚠️ QM-07 — HIGH: "โปรดระบุจำนวน ......คน" ระดับครัวเรือน ไม่มีฟิลด์เก็บ

### ⚠️ QM-08 — HIGH: ระดับน้ำท่วมมี 2 ช่อง (เมตร + เซนติเมตร) แต่ Schema มีช่องเดียว

**ปัญหาคืออะไร:** กระดาษเขียน `ระบุ...........เมตร.............เซ็นติเมตร` = **2 ช่องแยกกัน**
Schema มี `maxFloodDepthCm Int?` เพียงช่องเดียว (schema.prisma:954) พร้อม CHECK 0–1000 (BR-10)

**ผลกระทบ:**
1. **ผู้คีย์ต้องคำนวณเอง** (2 เมตร 50 ซม. → 250) → ขัด FR-ENT-01 ("ฟอร์มเรียงตรงกระดาษ 100%") และ PE6 (ตีความต่างกัน)
2. **ระดับน้ำสูงสุดเป็น Critical Field ⭐** → Entry 1 กับ Entry 2 อาจคำนวณต่างกัน หรือคนหนึ่งกรอก `2` (เมตร) อีกคนกรอก `250` (ซม.) → **Discrepancy เท็จ** ที่ Verifier ต้องมานั่งตัดสินโดยไม่จำเป็น
3. **กรณีที่อันตรายที่สุด:** ผู้สำรวจเขียนแค่ `2` ในช่องเมตร และเว้นช่องเซนติเมตร → ถ้าคีย์เป็น `2` → ระบบอ่านเป็น 2 **เซนติเมตร** แทนที่จะเป็น 200 → **Risk Score ผิดพลาดร้ายแรง** (FLOOD_DEPTH มีน้ำหนัก 15/115)
4. ค่าดิบหาย — ตรวจย้อนหลังไม่ได้

**แนวทางแก้ไข:**
1. เพิ่ม `floodDepthMetersRaw Int?` + `floodDepthCmRaw Int?` — **2 ช่องตรงกระดาษ** (📋)
2. `maxFloodDepthCm` = **Derived** = `(metersRaw × 100) + cmRaw` (Pure Function + Unit Test)
3. **Double-entry เทียบที่ 2 ช่องดิบ** ไม่ใช่ค่าที่คำนวณแล้ว
4. Validation: `cmRaw` ควร 0–99 (เตือนถ้าเกิน — อาจแปลว่าผู้สำรวจเขียน 150 ซม. ในช่อง ซม.)
5. คง CHECK รวม ≤1000 ซม. (10 เมตร) ตาม BR-10

### 3. มี Field ซ้ำกันหรือไม่?

**พบความซ้ำซ้อนเชิงแนวคิด 2 จุด:**
1. `Household.hasVulnerable` (Boolean) vs การมีอยู่ของแถวใน `VulnerablePerson` → ข้อมูลซ้ำที่อาจขัดกันเอง — **แต่จำเป็น** เพราะต้องแยก EXPLICIT_NONE ออกจาก BLANK_IN_PAPER → ต้องมี Validation กันขัดแย้ง
2. `PaperBatch.receivedCount` / `enteredCount` / `verifiedCount` เป็น Denormalized Counter ที่ซ้ำกับข้อมูลใน `PaperSheet` → ต้องพึ่ง Trigger ที่ปัจจุบัน**ทำงานไม่ครบ** (ดู SQL-05)
3. `Household.batchId` ซ้ำกับ `Household.sheet.batchId` → เป็น Denormalize ที่ตั้งใจ (มี Comment อธิบาย) ✅ แต่ไม่มีอะไรกัน 2 ค่าไม่ตรงกัน

### 5. มี Required Field ที่ควรเป็น Optional หรือไม่?

**Schema ทำถูกแล้วเป็นส่วนใหญ่** — เกือบทุกฟิลด์ที่มาจากกระดาษเป็น Nullable ✅ ซึ่งถูกต้องตาม CLAUDE.md

**ยกเว้น 2 จุดที่ยังเป็น Required และควรทบทวน:**
1. `Household.communityId String` (NOT NULL) — แต่กระดาษให้เขียนชื่อชุมชนเอง ซึ่งอาจอ่านไม่ออก → ถ้า ILLEGIBLE จะบันทึกไม่ได้ (ดู QM-01)
2. `Household.enteredById String` (NOT NULL) ✅ ถูกต้อง (ระบบเป็นคนใส่ ไม่ใช่กระดาษ)
3. `VulnerablePerson.seq Int` (NOT NULL) ✅ ถูกต้อง

### 6. มีคำตอบ "ไม่มี", "ไม่ทราบ", "เว้นว่าง" และ "อ่านไม่ออก" แยกกันหรือไม่?

**แยกได้ในเชิงโครงสร้าง แต่ไม่ครบทุกข้อ**

| สถานะ | กลไก | ครบหรือไม่ |
|---|---|---|
| **"อ่านไม่ออก"** (ILLEGIBLE) | `FieldStatusEnum.ILLEGIBLE` + F2 | ✅ ครบ — `FieldStatus` เก็บรายฟิลด์ผ่าน `fieldPath` |
| **"เว้นว่าง"** (BLANK_IN_PAPER) | `FieldStatusEnum.BLANK_IN_PAPER` + F3 | ✅ ครบ |
| **"ไม่มี"** (EXPLICIT_NONE) | `FieldStatusEnum.EXPLICIT_NONE` | ⚠️ **ไม่ครบ** — ส่วนที่ 2 ข้อ 1 มี `hasVulnerable` รองรับ ✅ แต่ **ส่วนที่ 3 ข้อ 11 ("☐ ไม่มี")** และ **ส่วนที่ 4 ข้อ 4 ("☐ ไม่สะดวก")** ไม่มีฟิลด์รองรับ (QM-09, QM-12) |
| **"ไม่ทราบ"** (UNKNOWN) | — | ⚠️ กระดาษมี "ไม่ทราบ" **เฉพาะส่วนที่ 3 ข้อ 8** (จุดอพยพใกล้สุด) ซึ่ง enum `NearestEvacSiteType.UNKNOWN` รองรับ ✅ — **แต่ "ไม่ทราบ" ≠ "เว้นว่าง" ≠ "ไม่มี"** ทั้ง 3 ต้องแยกกัน ซึ่งข้อ 8 ทำได้ (UNKNOWN = ติ๊กไม่ทราบ, BLANK = ไม่ติ๊ก) ✅ |

**⚠️ ช่องโหว่เชิงสถาปัตยกรรม:** `FieldStatus` ผูกกับ `sheetId` + `fieldPath` (String) — ยืดหยุ่นดี แต่**ไม่มีการบังคับว่า `fieldPath` ต้องถูกต้อง** → พิมพ์ผิดเป็น `"respondentPhoen"` ก็บันทึกได้ และจะหาไม่เจอตลอดไป → ควรมี `CriticalFieldConfig`/`FieldRegistry` เป็นแหล่งอ้างอิง `fieldPath` ที่ถูกต้อง (ดู GAP-R03)

### 7. หญิงตั้งครรภ์เก็บอายุครรภ์และสถานะข้อมูลอย่างเหมาะสมหรือไม่?

**ไม่เหมาะสม — มี 3 ปัญหา**
1. ❌ **หน่วยไม่ชัด** — กระดาษไม่ระบุ แต่ Schema บังคับสัปดาห์ + CHECK 1–42 (QM-06)
2. ⚠️ **สถานะข้อมูลไม่ครบ** — `PersonVulnerability` **ไม่มี** `FieldStatusEnum` สำหรับ `pregnancyWeeks` (ต่างจาก `VulnerablePerson` ที่มี `fullNameStatus`/`ageStatus`/`phoneStatus`) → ถ้าอายุครรภ์อ่านไม่ออก จะบันทึกอย่างไร? ต้องพึ่ง `FieldStatus` ทั่วไปผ่าน `fieldPath` ซึ่งไม่มีการรับประกันความถูกต้อง
3. ✅ **`referenceDate` ออกแบบถูกต้อง** — มี `referenceDate = household.surveyedAt` + Comment อธิบายการคำนวณอายุครรภ์ปัจจุบันและ Flag stale เมื่อเกิน 42 สัปดาห์ (schema.prisma:911-914) → ตรงกับ FR-VUL-08 และ BR-48 ✅ **แต่เป็นเพียง Comment — ยังไม่มีโค้ด**

### 8. มารดาหลังคลอดเก็บวันที่คลอดหรืออายุเด็กอย่างเหมาะสมหรือไม่?

**เหมาะสมกว่าข้อ 7 แต่ยังมีจุดอ่อน**
- ✅ กระดาษระบุหน่วยชัด: "ระบุ **อายุเดือนของเด็ก**" → `postpartumMonths Int?` ตรงกับกระดาษ
- ✅ Seed `detailLabel` = "ระบุอายุเดือนของเด็ก" ตรงกับกระดาษ 100%
- ⚠️ **ไม่เก็บวันที่คลอด** — เก็บเพียง "อายุเด็ก ณ วันสำรวจ" → ต้องพึ่ง `referenceDate` ในการคำนวณอายุปัจจุบัน ซึ่งถูกต้องตามหลัก **แต่แม่นยำน้อยกว่า** (เดือนมีความยาวไม่เท่ากัน และ "3 เดือน" อาจหมายถึง 2.5–3.5 เดือน)
- ⚠️ **ไม่มี CHECK constraint** สำหรับ `postpartumMonths` (ต่างจาก `pregnancyWeeks` ที่มี CHECK 1–42) → ควรมี 0–24 (นิยาม "หลังคลอด" ควรได้รับการยืนยัน — ดู Q-16)
- ⚠️ **ไม่มีกฎว่าเมื่อไหร่หมดสถานะ** — เด็ก 6 เดือน ณ วันสำรวจ ผ่านไป 1 ปี ยังเป็น "มารดาหลังคลอด" อยู่หรือไม่? → ต้องมี Stale Rule เหมือน `triageStale`
