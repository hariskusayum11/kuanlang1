# 31 — บัญชีคุ้มครอง (Protected Account)

**Owner Decision 2026-10-17** · สถานะ: **บังคับใช้แล้ว**

---

## 1. ปัญหาที่แก้

เดิม **ADMIN ทุกคนเท่ากันหมด** ด่านป้องกันที่มีอยู่มีเพียง 2 อย่าง และไม่ได้ปกป้องบัญชีใดเป็นการเฉพาะ:

| ด่านเดิม | ป้องกันอะไร | ไม่ป้องกันอะไร |
|---|---|---|
| `SELF_*` (ห้ามทำกับตัวเอง) | เผลอลบ/ปิดบัญชีตัวเอง | คนอื่นมาลบเรา |
| `LAST_ACTIVE_ADMIN` | ระบบไม่เหลือ ADMIN | ถ้ามี ADMIN 3 คน ลบออก 1 ได้สบาย |

ผลคือ **ADMIN คนใดก็ลบบัญชี ADMIN อีกคนได้** · ปิดบัญชีได้ · ถอดบทบาทได้ · และ
(หลังมีฟีเจอร์รหัสผ่านชั่วคราว ดู [30](30-email-system-toggle.md)) **ตั้งรหัสผ่านให้บัญชีนั้น
แล้วเข้าระบบในชื่อเขาได้** ซึ่งอันตรายกว่าการลบ เพราะ Audit Log จะบันทึกว่าเป็นเจ้าตัวที่ทำ

---

## 2. กฎ

`User.isProtectedAccount = true` แปลว่า:

| ใครทำ | กับบัญชีคุ้มครอง | ผล |
|---|---|---|
| ADMIN ธรรมดา | ลบ / ปิด-เปิด / ถอดบทบาท / ตั้งรหัสผ่าน / ตั้ง global scope | ❌ `PROTECTED_ACCOUNT` + เขียน Audit `REJECT` |
| **บัญชีคุ้มครองด้วยกัน** | เหมือนข้างบน | ✅ ทำได้ |
| เจ้าตัวเอง | — | กฎ `SELF_*` เดิมบังคับตามปกติ (ห้ามลบ/ปิดตัวเอง) |

การตั้ง/ถอดธง:

* **เฉพาะบัญชีคุ้มครองเท่านั้น** ที่ตั้งให้ผู้อื่นได้ — `user.manage` อย่างเดียวไม่พอ
  มิฉะนั้น ADMIN ธรรมดาจะแต่งตั้งตัวเองแล้วเดินผ่านกฎทั้งหมดในคลิกเดียว
* **ถอดบัญชีคุ้มครองคนสุดท้ายไม่ได้** — เหลือศูนย์เมื่อใดจะตั้งกลับจากในระบบไม่ได้อีก
  (หลักเดียวกับ `LAST_ACTIVE_ADMIN`) ตรวจภายใต้ `pg_advisory_xact_lock` คนละ key กับ
  invariant ของ ADMIN เพราะเป็นคนละเรื่อง
* **บัญชีคุ้มครองคนแรกตั้งจากนอกระบบเท่านั้น** (สคริปต์บนเซิร์ฟเวอร์)

> ธงนี้ **ไม่ใช่ Role และไม่ให้สิทธิ์เพิ่มใด ๆ** — ให้เพียง "ความคุ้มกัน"
> ชื่อจึงเรียกตามหน้าที่ ไม่ได้สื่อความเป็นเจ้าของหรือลำดับอาวุโส

---

## 3. วิธีใช้

### ตั้งบัญชีคุ้มครองคนแรก (บนเซิร์ฟเวอร์)

```bash
docker compose exec app npm run account:protect -- someone@example.com
```

สคริปต์ **มอบบทบาท ADMIN ให้อัตโนมัติถ้ายังไม่มี** — บัญชีคุ้มครองที่ไม่มี ADMIN จะกลายเป็น
"ใครแตะไม่ได้ แต่ตัวเองก็ทำอะไรไม่ได้" และตั้งบัญชีคุ้มครองให้คนอื่นไม่ได้ด้วย

ถอด: เติม `--off` · รันซ้ำได้ (idempotent) · ทุกครั้งเขียน Audit Log

### ตั้งให้คนอื่นภายหลัง

หน้า `/admin/users` → ปุ่ม **"ตั้งเป็นบัญชีคุ้มครอง"** (ปรากฏเฉพาะเมื่อผู้ใช้งานเป็นบัญชีคุ้มครองเอง)

---

## 4. ความปลอดภัย — ขอบเขตที่แท้จริง

### กันได้

ADMIN ในระบบ: ลบบัญชี · ปิดบัญชี · ถอดบทบาท · **ตั้งรหัสผ่านแล้วสวมรอย** ·
แต่งตั้งตัวเองเป็นบัญชีคุ้มครอง · สร้างบัญชี ADMIN ใหม่มาเล่นงาน

ระบบไม่มีฟีเจอร์แก้อีเมลของผู้อื่นอยู่แล้ว จึงไม่มีช่องยึดบัญชีผ่านการเปลี่ยนอีเมล

### กันไม่ได้ (ข้อจำกัดเชิงหลักการ)

| ภัย | เหตุผล |
|---|---|
| ผู้ที่เข้าถึง **เซิร์ฟเวอร์** ได้ | รัน `npm run account:protect` ตั้งตัวเองได้ |
| ผู้ที่เข้าถึง **ฐานข้อมูล** ได้ | `UPDATE "user" SET "isProtectedAccount" = true` |

ธงนี้กัน **"ADMIN ในระบบ"** ไม่ได้กัน **"ผู้ที่อยู่นอกระบบ"** —
ความปลอดภัยชั้นนั้นเป็นเรื่องของการจัดการสิทธิ์เข้าถึงเซิร์ฟเวอร์ ไม่ใช่ของโค้ด

### เรื่องที่อยู่นอกขอบเขตของกลไกนี้

ADMIN ธรรมดา **ยังลบ ADMIN ธรรมดาด้วยกันได้** — ธงนี้คุ้มครองเฉพาะบัญชีที่ถูกตั้งไว้เท่านั้น

---

## 5. ความเสี่ยงหลักของกลไกนี้ และวิธีคุม

**ความเสี่ยง:** เพิ่มการกระทำทำลายล้างใหม่ในอนาคตแล้วลืมใส่ guard → ช่องโหว่กลับมาเงียบ ๆ

**วิธีคุม:**

1. เงื่อนไขทั้งหมดอยู่ใน Pure Function เดียว `domain/admin/protected-account.ts`
2. `PROTECTED_ACTIONS` เป็นรายการกลางของการกระทำที่ต้องถูกคุ้มครอง
3. `tests/integration/protected-account.test.ts` **ไล่ทุกค่าใน `PROTECTED_ACTIONS`**
   ว่าถูกปฏิเสธจริง และมีเทสต์ยืนยันว่า "ตารางเคสครอบคลุมครบทุกค่า"
   → เพิ่มการกระทำใหม่ในรายการแต่ไม่เขียนเคส เทสต์จะฟ้องทันที
