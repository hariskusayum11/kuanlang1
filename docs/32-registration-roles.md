# 32 — การสมัคร การอนุมัติ และบทบาท

**Owner Decision 2026-10-18** · สถานะ: **บังคับใช้แล้ว**

---

## 1. ปัญหาที่แก้

| ปัญหาเดิม | ผล |
|---|---|
| **ผู้บริหารสมัครเองได้** | ใครก็สมัครขอเป็น `EXECUTIVE` ได้ ซึ่งเปิดดูข้อมูลสุขภาพรายบุคคลและดาวน์โหลด Excel รายชื่อกลุ่มเปราะบางพร้อม**พิกัดบ้าน**ได้ · หลังปิดระบบอีเมล ([30](30-email-system-toggle.md)) ไม่มีการยืนยันอีเมลช่วยกรองอีก เหลือดุลยพินิจ ADMIN อย่างเดียว |
| **ผู้สมัครเป็นคนกำหนดสิทธิ์ตัวเอง** | ADMIN ได้แค่ "อนุมัติ/ปฏิเสธ" ตามบทบาทที่ขอมา เปลี่ยนไม่ได้ — สมัครผิดช่องต้องอนุมัติผิดก่อนแล้วไปแก้ทีหลัง |
| **"เจ้าหน้าที่" สมัครไม่ได้** | ทั้งที่เป็นบทบาทที่ใช้งานจริง ต้องให้ ADMIN สร้างบัญชีให้เองทั้งหมด |
| **อาสาสมัครเข้ามาแล้วเจอแดชบอร์ดผู้บริหาร** | มีสิทธิ์เดียวคือ `dashboard.view` จึงเห็นตัวเลขรวมทั้งระบบ ทั้งที่ไม่มีโมดูลภารกิจให้ทำอะไร — ขัดกฎ "Volunteer เห็นเฉพาะข้อมูลที่จำเป็นต่อภารกิจ" |

---

## 2. หลักการใหม่

> **ผู้สมัครบอกว่า "ฉันคือใคร" · ADMIN ตัดสินว่า "ได้สิทธิ์อะไร"**

ไม่มีบทบาทใดถูกมอบด้วยการที่ผู้สมัครเลือกเองอีกต่อไป

### หน้าสมัคร — `REQUESTABLE_ROLES`

ช่อง "บทบาทที่ขอ" (ใช้ชื่อบทบาทตรง ๆ — เคยลองเปลี่ยนเป็นคำถาม "คุณคือใคร"
แต่เจ้าของระบบไม่ผ่าน จึงกลับมาใช้แบบเดิม)

| ตัวเลือก | ค่าที่เก็บ |
|---|---|
| เจ้าหน้าที่คีย์ข้อมูล | `DATA_ENTRY` |
| เจ้าหน้าที่ | `OFFICER` |
| อาสาสมัคร | `VOLUNTEER` |

ค่าที่เก็บเป็น "บทบาทที่ผู้สมัครขอ" ซึ่ง ADMIN เปลี่ยนได้ตอนอนุมัติ (**ไม่ต้อง migrate**)

หลังส่งคำขอขณะปิดระบบอีเมล หน้าจอบอกขั้นต่อไปเป็นลำดับ (รออนุมัติ → เข้าระบบด้วย
รหัสที่ตั้งไว้ได้ทันที) และไม่พูดถึงอีเมลยืนยันเลย เพื่อไม่ให้ผู้สมัครเฝ้ารอเมลที่ไม่มีวันมา

### หน้าอนุมัติ — `APPROVABLE_ROLES`

ADMIN เลือกบทบาทจริงจาก: **เจ้าหน้าที่คีย์ข้อมูล · เจ้าหน้าที่ · ผู้บริหาร/แพทย์ · อาสาสมัคร**
ค่าเริ่มต้นคือบทบาทที่ผู้สมัครเสนอมา

* **`ADMIN` ไม่อยู่ในรายการโดยตั้งใจ** — การยกสิทธิ์ผู้ดูแลระบบต้องทำที่หน้าจัดการผู้ใช้
  เพื่อไม่ให้เกิดขึ้นได้ด้วยการกดปุ่มเดียวในคิวอนุมัติ
* `EXECUTIVE` อยู่ในรายการ (แม้สมัครเองไม่ได้) เพราะ ADMIN ต้องมอบได้ **และ**
  คำขอเก่าที่ยื่นมาเป็น EXECUTIVE ก่อนเปลี่ยนกติกาต้องยังอนุมัติได้
* Audit บันทึก `requestedRole`, `grantedRole`, `roleChangedByAdmin` ทุกครั้ง
* ตรวจซ้ำฝั่ง server เสมอ — ค่าที่ client ส่งมาผ่านทั้ง schema ใน action และ whitelist ใน core

`recoverUser` (กู้คืนบัญชีที่ถูกปฏิเสธ) ใช้ `APPROVABLE_ROLES` ชุดเดียวกัน

## 3. อาสาสมัคร — รับไว้ แต่ไม่ให้เห็นเกินจำเป็น

เจ้าของระบบเลือก **"รับไว้ + หน้ารอภารกิจ"** แทนการปิดรับ เพราะระบบนี้คือระบบภัยพิบัติ
การมีรายชื่อผู้สมัครใจพร้อมเบอร์โทรไว้ **ก่อน**เกิดเหตุมีค่ามาก

| | เดิม | ตอนนี้ |
|---|---|---|
| Permission | `dashboard.view` | `volunteer.portal.view` |
| หน้าแรกหลังเข้าระบบ | `/dashboard` (แดชบอร์ดผู้บริหาร) | `/volunteer` |
| เห็นตัวเลขรวมของระบบ | ✅ เห็น | ❌ ไม่เห็น |

หน้า `/volunteer` แสดงเฉพาะ **ข้อมูลของตัวผู้ใช้เอง** (ชื่อ/เบอร์/อีเมล/สังกัด) และ
**เบอร์ฉุกเฉินสาธารณะ** — ไม่มีข้อมูลครัวเรือน ไม่มีตัวเลขรวม

เป็นหน้าสื่อสารกับประชาชนจึงใส่มาสคอตได้ตามกฎ F (ต่างจากหน้าหลังบ้าน)

> ตาราง `VolunteerProfile` ในฐานข้อมูลยังว่างอยู่ — จะใช้เมื่อทำโมดูลภารกิจ/เหตุการณ์

---

## 4. สิ่งที่ **ไม่** เปลี่ยน

* `EXECUTIVE` ยังดาวน์โหลด Excel รายชื่อกลุ่มเปราะบางได้ (`medical.report.export`) —
  เจ้าของระบบยืนยันให้คงไว้ เพราะผู้บริหารของโครงการคือแพทย์ที่ต้องใช้ข้อมูลวางแผนช่วยเหลือ
* `EXECUTIVE` ยังเป็นบทบาทเดียวที่รวม "ผู้บริหาร" กับ "แพทย์" ไว้ด้วยกัน —
  ถ้าวันหน้ามีผู้บริหารที่ไม่ใช่แพทย์ ควรแยกบทบาท (ยังไม่จำเป็นตอนนี้)
* บทบาทเดิมที่เลิกใช้ (COORDINATOR / VERIFIER / FIELD_SURVEYOR) ยังมอบใหม่ไม่ได้ตาม #R6-D
