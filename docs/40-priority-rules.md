# 40 — กฎการจัดลำดับ (ความเร่งด่วน + ความเสี่ยง) และลำดับการช่วยเหลือบนแผนที่

**Owner Decision 2026-10-19** (ประชุม ข้อ 7–8) · สถานะ: **บังคับใช้แล้ว — ค่าในกฎยังเป็นร่าง รอเจ้าของระบบรับรอง**

## สิ่งที่เจ้าของระบบตัดสิน
1. **ทุกฝ่ายต้องเห็นกฎปัจจุบันก่อน** แล้ว ADMIN จึงแก้ได้ — ภาษาไทยล้วน
   · **2026-10-21:** อาจารย์ขอให้เห็นเกณฑ์ **บนหน้าที่ใช้จริง** — ดู "กล่องเกณฑ์บนหน้า /medical และ /risk" ด้านล่าง
2. การแก้ **ไม่เขียนทับ**: ทุกครั้งเป็นเวอร์ชันใหม่ พร้อมผู้แก้ เวลา เหตุผล และ Audit Log ค่าก่อน/หลัง
3. ต้อง **ดูผลกระทบก่อนบันทึก** (เช่น "วิกฤต 82 → 95 คน", "บ้านสูงมาก 40 → 52 หลัง")
4. **ห้ามมีรหัส P1/P2/P3 บนหมุด** — ใช้คำไทย (วิกฤต / เร่งด่วน / เฝ้าระวัง) ในคำอธิบายสัญลักษณ์และรายการ
5. แผนที่ภายในต้องบอก **"ช่วยใครก่อน"** โดยไม่มีบ้านหายจากรายการ

## กล่องเกณฑ์บนหน้า /medical และ /risk (Owner Decision 2026-10-21)
แทนเมนู "กฎการจัดลำดับ" แยก — เกณฑ์แสดงตรงหน้าที่ตัวเลขถูกใช้:

| หน้า | สรุปที่เห็นทันที | "ดูเกณฑ์ทั้งหมด" (กางในที่) |
|---|---|---|
| `/medical` ข้อมูลสุขภาพและกลุ่มเปราะบาง | วิกฤต / เร่งด่วน / เฝ้าระวัง + ภายใน 30 นาที / 2 ชม. / 6 ชม. + ลักษณะความเปราะบางที่ใช้งานในแต่ละระดับ · ป้ายร่าง | วิธีให้ระดับรายคน · ลักษณะที่ปิดใช้งาน · ลำดับช่วยเหลือบนแผนที่ · ประวัติ 5 เวอร์ชันล่าสุด |
| `/risk` ความเสี่ยงและการช่วยเหลือ | ปัจจัย + น้ำหนัก (คะแนนเต็ม) · ปัจจัยที่ยังไม่มีข้อมูล · เกณฑ์ ต่ำ/ปานกลาง/สูง/สูงมาก · ความมั่นใจขั้นต่ำ · กฎบังคับ · รุ่นสูตร/น้ำหนัก | ตารางปัจจัยเต็ม · ข้อมูลขาด · สูตรความมั่นใจ · ลำดับช่วยเหลือ · ประวัติ |

- หัวกล่องแสดง **เวอร์ชัน + ร่าง/รับรองแล้ว** เสมอ · ทุกคำเป็นภาษาไทย (ชื่อปัจจัย `HAS_P1`/`HAS_P2` ที่เก็บใน config
  ยังมีรหัส P — หน้าจอแปลงเป็น "มีคนระดับวิกฤต/เร่งด่วนในบ้าน" ผ่าน `factorLabel()` โดยไม่แก้ข้อมูลที่เก็บ)
- **ADMIN** เห็นปุ่ม "แก้เกณฑ์" → เปิด `RuleEditor` เดิม (แก้ → ดูผลกระทบ → เหตุผล → บันทึกเวอร์ชันใหม่) ใน `Modal` (portal)
  บันทึกแล้วปิดกล่อง แสดงผลบันทึก และ `router.refresh()` · บทบาทอื่นไม่ได้รับ props ของตัวแก้เลย และ server action ตรวจ
  `priority-rules.manage` ซ้ำทุกครั้ง (การซ่อนปุ่มไม่ใช่การกันสิทธิ์)
- กล่องแสดงเมื่อบัญชีดูกฎได้ (`canViewRules`) — บัญชีที่เปิด `/medical` หรือ `/risk` ได้แต่ไม่มี `dashboard.view` จะไม่เห็นกล่อง
- **หน้า `/priority-rules` ยังเปิดได้** (ลิงก์ "เปิดหน้ากฎการจัดลำดับฉบับเต็ม" ในกล่อง และจากแผงลำดับช่วยเหลือบนแผนที่)
  แต่ **ไม่มีเมนูใน Sidebar แล้ว** — ส่วนแสดงผลทั้งสามที่ใช้ชิ้นเดียวกันอยู่ที่ `components/rules/rule-sections.tsx`

## โครงสร้างข้อมูล
ตารางใหม่ `priority_rule_version` (migration `20261020030000_priority_rule_version` — เพิ่มอย่างเดียว ย้อนกลับด้วย `DROP TABLE`)

| คอลัมน์ | ความหมาย |
|---|---|
| `versionNo` | 1, 2, 3 … (unique — สองคนบันทึกพร้อมกันได้ CONFLICT ไม่ทับกัน) · เวอร์ชันที่ใช้ = สูงสุด |
| `isDraft` | `true` = ยังไม่รับรอง → หน้า `/risk`, `/map`, `/priority-rules` แสดงป้าย "ร่าง" |
| `riskConfig` | `RiskWeightConfig` ทั้งชุด (ตรวจด้วย Zod ตอนอ่าน — อ่านไม่ได้ → ใช้ค่าร่างในโค้ด) |
| `triageMap` | สำเนาการจับคู่ประเภท → P1/P2/P3 ณ เวอร์ชันนั้น (เพื่อประวัติ) |
| `reason`, `createdById`, `createdAt` | ใคร เมื่อไร เพราะอะไร |

- Append-only: แอปไม่มีคำสั่ง UPDATE/DELETE ตารางนี้ (เทสต์ integration ลบเฉพาะเวอร์ชันที่ตัวเองสร้าง)
- Seed (`prisma/seed.ts` ข้อ 14) สร้างเวอร์ชัน 1 = `DRAFT_RISK_CONFIG_V1` + การจับคู่ตั้งต้น แบบ `update: {}` (seed ซ้ำไม่ย้อนกฎ)
- ไม่มีแถวเลย → ใช้ค่าร่างในโค้ด (เวอร์ชัน 0) · ตาราง `risk_weight_config` เดิมยังไม่ถูกใช้ (คงไว้ ไม่ลบ)

## ความเร่งด่วนรายบุคคลเมื่อแก้การจับคู่
ค่าที่ใช้จริงยังอยู่ที่ `VulnerabilityType.basePriority` (หน้าตรวจใบ/รายงานอ่านจากที่นี่) — การบันทึกเวอร์ชันใหม่จึง:
1. อัปเดต `basePriority` ของประเภทที่เปลี่ยน
2. ย้าย `VulnerablePerson.triageLevel` ที่บันทึกไว้ **เฉพาะคนที่ระดับเท่ากับที่เกณฑ์เดิมแนะนำ** (ถือว่าตั้งอัตโนมัติตอนตรวจใบ)
3. **คนที่ผู้ดูแลปรับเองจากรายงาน (ระดับ ≠ เกณฑ์เดิม) คงไว้** · คนที่ยังไม่บันทึกระดับใช้เกณฑ์ใหม่ทันที

ทั้งหมดอยู่ใน transaction เดียวกับการสร้างเวอร์ชันและ Audit Log (`entityType = PriorityRuleVersion`, `changes.items` = old → new)
กติกาเป็น Pure Function `storedTriageAfterMapChange` (`domain/rules/impact.ts`)

## สิ่งที่แก้ได้ / แก้ไม่ได้
- **แก้ได้:** ระดับของแต่ละประเภทความเปราะบาง · น้ำหนัก 12 ปัจจัย (0–100 ทีละ 0.5) · เกณฑ์ ต่ำ < ปานกลาง < สูง < 100 ·
  ความมั่นใจขั้นต่ำ · ระดับขั้นต่ำของกฎบังคับ (ติดเตียง/ฟอกไต) · ธง "รับรองแล้ว"
- **แก้ไม่ได้ (ผูกกับโค้ด):** เพิ่ม/ลบปัจจัย · วิธีแปลงคำตอบเป็น 0–1 (100 ซม., 7 วัน, ต่ำกว่าถนน = 1) ·
  สูตร confidence (0.7 + 0.3 × ตรวจแล้ว) · ระยะเวลาเข้าช่วย 30 นาที / 2 ชม. / 6 ชม. (แสดงเป็นข้อมูล)

## ลำดับการช่วยเหลือบนแผนที่ (`/map?help=on`)
เรียง (`domain/geo/help-priority.ts`): ความเร่งด่วนสูงสุดของบ้าน (วิกฤต → เร่งด่วน → เฝ้าระวัง → ยังไม่ประเมิน → ไม่มีกลุ่มเปราะบาง)
→ คะแนนความเสี่ยงสัมบูรณ์ → ความมั่นใจ → รหัสใบ

- ทุกครัวเรือน VERIFIED ตามตัวกรองชุมชน/ตำบล/วันที่ — **ไม่มีเพดาน** · บ้านที่ไม่มีพิกัดอยู่ในรายการพร้อมป้าย "ไม่มีพิกัด"
- หมุดเป็นตัวเลขลำดับ สีจาก `.map-urgency-*` (แดง = วิกฤตเท่านั้น) · บ้านไม่มีกลุ่มเปราะบาง = พื้นขาวขอบเทา
- รายการอยู่ในแท็บ "ลำดับการช่วยเหลือ" ของแผงข้าง — กดแล้วซูมไปที่บ้านและเปิดกล่องข้อมูล
- ระหว่างเปิดชั้นนี้ หมุดชั้นครัวเรือนอื่นซ่อนชั่วคราว (ไม่ให้ซ้อนกัน) · ฮีตแมปและจุดสำคัญยังเปิดได้
- ไม่ส่งชื่อ เบอร์ หรือโรคออกจาก server · Audit READ (`HelpPriorityMap`)

## การเปลี่ยนแปลงที่กระทบหน้าเดิม
- `/risk` ใช้กฎเวอร์ชันที่ใช้งาน และคำนวณ **ทุกครัวเรือน** (ถอด `RISK_LIST_LIMIT = 500` ซึ่งทำให้บ้านหลังที่ 501 หายเงียบ)
- เกณฑ์ "ใบที่ใช้ได้" ของ `/risk` เปลี่ยนจาก `hasDuplicateFlag = false` เป็นเกณฑ์เดียวกับแผนที่/แดชบอร์ด
  (`buildVerifiedMapHouseholdWhere`: ตัดเฉพาะใบที่ผู้ตรวจยืนยันว่าซ้ำจริง) — ตัวเลข `/risk` กับแผนที่จึงตรงกัน
- คำนวณสดทุกครั้ง (ไม่ persist ลง `FloodRiskProfile`) — ข้อมูลหลักพันหลังยังเร็วพอ ถ้าข้อมูลโตมากค่อยพิจารณาเก็บผลไว้
