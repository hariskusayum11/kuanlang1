## ทำไมต้องรับรองก่อน

Risk Score เป็นตัวเลขที่ตัดสินว่า **"คืนที่น้ำท่วมจริง จะไปช่วยบ้านไหนก่อน"**
ถ้าน้ำหนัก/เกณฑ์ผิด ระบบจะจัดลำดับผิด → คนที่ควรได้รับการช่วยเหลือก่อนอาจตกลำดับ
CLAUDE.md จึงบังคับว่า *"ก่อนใช้ Risk Model ต้องตรวจสอบ... Version ของสูตรความเสี่ยง"*
และเอกสาร 08 ย้ำว่าน้ำหนัก/threshold/สูตร confidence **"ไม่มีเอกสารอ้างอิงว่ามาจากไหน"**

**สถานะปัจจุบันในโค้ด (ยืนยันแล้ว):**
- `FloodRiskProfile` เก็บได้แค่ `rawScore`/`maximumPossibleScore`/`normalizedScore` (ค่าว่าง) — ไม่มี logic คำนวณ
- ยังไม่มี `absoluteScore`, `riskConfidence`, `riskLevelAuto`, Hard Rules ในสคีมา
- น้ำหนัก **ยังไม่ถูก seed** ลงฐานข้อมูลเลย

### ชุด 2 — เกณฑ์แบ่งระดับ (Threshold) + ใช้คะแนนตัวไหนจัดระดับ

**2.1 ใช้คะแนนตัวไหนจัดระดับ?** (ข้อเสนอ: `absoluteScore` = rawScore / 115 × 100)

เหตุผลที่ **ไม่ใช้** `normalizedScore`: ถ้าใช้ normalized ครัวเรือนที่มีข้อมูลแค่ปัจจัยเดียว
(เช่น รู้แค่ "พื้นต่ำกว่าถนน") จะได้ 100 คะแนน = CRITICAL ปลอม สูงกว่าบ้านที่ข้อมูลครบ
และเสี่ยงจริง → `absoluteScore` (ตัวหารคงที่ 115) เทียบข้ามครัวเรือนได้ยุติธรรม

**2.2 เกณฑ์ระดับ** (ข้อเสนอ: half-open interval ปิดช่องว่าง ไม่ให้ค่า 25.5 ตกช่อง)

| ระดับ | ช่วงเสนอ | เงื่อนไข | รับรอง (✓/ปรับ) |
|---|---|---|---|
| LOW (ต่ำ) | 0–25 | `score <= 25` | |
| MEDIUM (ปานกลาง) | >25–50 | `25 < score <= 50` | |
| HIGH (สูง) | >50–75 | `50 < score <= 75` | |
| CRITICAL (สูงมาก) | >75–100 | `score > 75` | |

> ⚠️ ตัวเลข 25/50/75 **ไม่มีที่มา** — ต้องรับรองว่าเหมาะกับบริบทควนลังหรือปรับใหม่

### ชุด 3 — สูตร Confidence (ความมั่นใจของคะแนน) + เกณฑ์ขั้นต่ำ

**3.1 สูตรที่เสนอ** (ถ่วงน้ำหนัก ไม่ใช่นับจำนวนปัจจัย):

```
dataCompleteness  = น้ำหนักที่มีข้อมูล / 115
verificationLevel = น้ำหนักที่ผ่านการตรวจสอบ / น้ำหนักที่มีข้อมูล
riskConfidence    = dataCompleteness × (0.7 + 0.3 × verificationLevel)
```

รับรองน้ำหนัก 0.7 / 0.3:  ☐ ใช่   ☐ ปรับเป็น: ______ / ______

**3.2 เกณฑ์ขั้นต่ำที่จะ"กล้าแสดงระดับ"** (มีในระบบแล้ว `RISK_MIN_CONFIDENCE = 0.6`):

- ถ้า `riskConfidence >= 0.6` → แสดงระดับความเสี่ยงตามปกติ
- ถ้า `< 0.6` → แสดง **"ข้อมูลไม่พอประเมิน"** (สีเทา) + ห้ามใช้ในลิสต์ช่วยเหลือ

### ชุด 4 — การตีความข้อมูลขาด (BLANK / ILLEGIBLE / ไม่มีจริง)

ข้อเสนอ (สำคัญมาก — ป้องกัน "ความเสี่ยงปลอมจากช่องว่าง"):

| สถานะฟิลด์ | ความหมาย | คิดเป็นความเสี่ยง? | นับใน confidence? |
|---|---|---|---|
| มีค่าจริง (`HAS_VALUE`) | ตอบมา | ✅ ตามค่า | ✅ นับ |
| ติ๊ก "ไม่มี" จริง (`EXPLICIT_NONE`) | ยืนยันว่าไม่มี เช่น ไม่มีรถ | ✅ เป็นความเสี่ยง | ✅ นับ |
| กระดาษเว้นว่าง (`BLANK_IN_PAPER`) | ไม่ได้ถาม/ไม่ได้ตอบ | ❌ ตัดออก | ❌ ไม่นับ → ลด confidence |
| อ่านไม่ออก (`ILLEGIBLE`) | ลายมืออ่านไม่ได้ | ❌ ตัดออก | ❌ ไม่นับ → ลด confidence |

รับรองหลักการนี้:  ☐ ใช่   ☐ ปรับ: __________

> ⚠️ ข้อจำกัดที่ต้องรับทราบ: ปัจจัย `NO_VEHICLE` และ `NO_DIGITAL_CHANNEL` ในกระดาษ
> **ไม่มีช่อง "ไม่มี" ชัดเจน** → แยก "ไม่มีจริง" จาก "ไม่ได้ถาม" ไม่ได้
> ข้อเสนอ: ถือเป็น BLANK (ไม่นับ) ไว้ก่อน เพื่อไม่สร้างความเสี่ยงปลอม แล้วแก้กระดาษรอบหน้า

## หลังรับรองแล้ว — ขั้นพัฒนาที่จะตามมา (ประเมินไว้ให้เห็นภาพ)

1. **Pure Function Engine** (`domain/risk/`) + Unit Test — คำนวณ 4 คะแนน, confidence 3 มิติ, จัดระดับ, hard rules
2. **Migration** — เพิ่มฟิลด์ `absoluteScore`/`riskConfidence`/`riskLevelAuto`/ฯลฯ ลง `FloodRiskProfile`, แก้ CHECK 0-100, สร้างตาราง `RiskWeightVersion` + `RiskHardRule` (แทน `factorCode @unique` เดิม)
3. **Seed น้ำหนัก v1** (idempotent) จากค่าที่รับรอง
4. **บังคับ VERIFIED เท่านั้น** — ห้ามคำนวณ Risk จากข้อมูลที่ยังไม่ยืนยัน
5. **ต่อ Dashboard/GIS** — แสดงระดับ + confidence + denominator

> แต่ละขั้นทำหลังรับรอง และก่อน migration จะสร้าง commit สำรองตาม Git rules
