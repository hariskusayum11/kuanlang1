# 34 — หัวหน้าชุมชน และสถานะกลุ่มเปราะบางหลังการสำรวจ

**Owner Decision 2026-10-19** · สถานะ: **บังคับใช้แล้ว**

---

## 1. ปัญหาที่แก้

| ปัญหาเดิม | ผล |
|---|---|
| **ไม่มีทางบันทึกว่ามีคนเสียชีวิต/ย้ายออก** | ทางเดียวคือเปิดแบบสอบถามมาแก้แล้วลบแถวทิ้ง → แถวหายจริงโดยไม่มีวันที่/สาเหตุ · ใบที่ตรวจแล้วเด้งกลับไปรอตรวจ ทั้งครัวเรือนหายจากตัวเลข "ตรวจแล้ว" และลำดับการช่วยเหลือ · ข้อมูลในระบบไม่ตรงกระดาษอีกต่อไป |
| **ข้อมูลไม่เรียลไทม์** | คนที่รู้ก่อนคือหัวหน้าชุมชน แต่ไม่มีบัญชีในระบบ ต้องแจ้งต่อเป็นทอด ๆ |
| **การแก้ใบซ้ำล้างสถานะ** | การแก้ใบสร้างกลุ่มเปราะบางใหม่ทั้งชุด (#R7-C) — ถ้ามีสถานะไว้ คนที่เสียชีวิตจะ "กลับมานับ" เงียบ ๆ |

## 2. หลักการ

> **เสียชีวิต / ย้ายออก / ไม่เข้าเกณฑ์แล้ว = เหตุการณ์หลังการสำรวจ ไม่ใช่การแก้ข้อมูลกระดาษ**

- เก็บที่ `VulnerablePerson.isActive` + `deactivatedReason` (รหัส) + `deactivatedAt` (วันที่เกิดเหตุ) + `deactivatedById` (ผู้บันทึก)
- **ไม่เปลี่ยนสถานะใบ** — ใบที่ตรวจแล้วยังตรวจแล้ว
- หน้ารายงาน ส่งออก Excel ความเสี่ยง แผนที่ และเคสการแพทย์กรอง `isActive: true` อยู่แล้ว → **ตัวเลขทุกหน้าเปลี่ยนทันที** (คำนวณสดทุกครั้งที่เปิดหน้า)
- ไม่ลบข้อมูล · คืนสถานะได้ · Audit ทุกครั้ง

| รหัส | ป้าย | ความหมาย |
|---|---|---|
| `DECEASED` | เสียชีวิต | |
| `MOVED_OUT` | ย้ายออก | ไม่ได้อาศัยอยู่ที่บ้านหลังนี้แล้ว |
| `NO_LONGER_ELIGIBLE` | ไม่เข้าเกณฑ์แล้ว | เช่น คลอดแล้ว เด็กอายุเกิน 5 ปี หายป่วย |
| (คืนสถานะ) | ปกติ | ล้างค่าเหตุการณ์ทั้งหมด — ประวัติอยู่ใน Audit Log |

วันที่เกิดเหตุ: ไม่อยู่ในอนาคต และย้อนหลังไม่เกิน 5 ปี (กันพิมพ์ปี พ.ศ. ลงช่อง ค.ศ.) — ตรวจซ้ำที่ server ด้วยเวลาไทย

| ได้บัญชีอย่างไร | สมัครตามปกติ แล้ว ADMIN มอบบทบาท "หัวหน้าชุมชน" ตอนอนุมัติ (ไม่มีในตัวเลือกหน้าสมัคร) · ชุมชนที่ผู้สมัครเลือกไว้ถูกผูกอัตโนมัติ · แก้ได้ที่หน้า "ผู้ใช้และสิทธิ์" ปุ่ม "ชุมชน: …" |

### ข้อยกเว้นของ #R7-B (ยกเลิก Community Scope)

Community Scope ยังยกเลิกทั้งระบบตามเดิมสำหรับบทบาทอื่น — หน้านี้อ่าน `UserCommunityScope`
ผ่าน `resolveStatusScope()` (`domain/vulnerable/status.ts`) เพราะหัวหน้าชุมชนเห็นข้อมูลสุขภาพ
รายบุคคล · ไม่ดูธง `hasGlobalCommunityScope` โดยตั้งใจ (ธงนั้นไม่มีความหมายแล้วและอาจค้างค่าเดิม)

**ปรับ 2026-10-21 (เฟส 4):** `buildAuthorization()` ให้บัญชีหัวหน้าชุมชน `isGlobalScope: false`
แล้ว — แดชบอร์ด หน้าชุมชน และแผนที่จึงกรองตาม `UserCommunityScope` เดียวกัน ดู [41](41-community-leader-scope.md)

การกำหนดชุมชน (`setUserCommunities`) อยู่ใน `PROTECTED_ACTIONS` (`set-communities`) — ADMIN ทั่วไปแก้ให้บัญชีคุ้มครองไม่ได้

## 4. การแก้ใบภายหลัง — ย้ายสถานะข้ามการสร้างใหม่

`lib/entry/save.ts` ก่อนลบกลุ่มเปราะบางเดิม:

1. `SELECT … FOR UPDATE` ล็อกแถว — กันหัวหน้าชุมชนบันทึกแทรกระหว่าง "อ่าน" กับ "ลบ" (อีกฝั่งจะได้ `CONFLICT`)
2. อ่านแถวที่ `isActive = false` แล้วจับคู่กับแถวใหม่ด้วย `carryOverStatuses()`:
   - **จับคู่ด้วยชื่อเป็นหลัก ไม่ใช่ลำดับแถว** — ผู้คีย์อาจลบแถวที่ 2 ทำให้แถวเลื่อน ถ้าใช้ลำดับอย่างเดียว
     สถานะ "เสียชีวิต" จะไปติดคนที่ยังมีชีวิต (ผิดร้ายแรงกว่าหาย)
   - ชื่อซ้ำในบ้าน → ไม่เดา · แถวไม่มีชื่อ → จับคู่ลำดับเดียวกันที่ไม่มีชื่อเหมือนกัน
3. จับคู่ไม่ได้ (เช่น ผู้คีย์ลบคนนั้นออกจากใบ) → ทิ้ง และเขียน Audit `vulnerable-status-carry-over-on-reedit` พร้อมจำนวน

## 5. Audit

| เหตุการณ์ | action · entityType · reason |
|---|---|
| เปิดรายชื่อ | `READ` · `VulnerableStatusList` · `view-community-vulnerable-status` |
| เปลี่ยนสถานะ | `UPDATE` · `VulnerablePerson` · `vulnerable-status-change` — `{ status: {old,new}, eventDate: {old,new} }` |
| นอกขอบเขต | `REJECT` · `VulnerablePerson` · `vulnerable-status-out-of-scope` |
| กำหนดชุมชน | `UPDATE` · `UserCommunityScope` · `set-leader-communities` — `{ before, after }` |
| แก้ใบแล้วย้ายสถานะ | `UPDATE` · `VulnerablePerson` · `vulnerable-status-carry-over-on-reedit` — `{ carried, dropped }` |

ไม่มี PII ใน Audit (รหัสสถานะ วันที่ และ id เท่านั้น)

## 8. ยังไม่ได้ทำ (ตามจริง)

- **ครัวเรือนย้ายออกทั้งหลัง** — ตอนนี้ต้องบันทึกรายคน ระดับครัวเรือนยังไม่มีสถานะ
- **การแจ้งเตือนเจ้าหน้าที่** เมื่อหัวหน้าชุมชนบันทึก — ดูย้อนหลังได้จาก Audit Log และหน้านี้ (ADMIN เห็นทุกชุมชน) แต่ยังไม่มีการแจ้งเตือนเชิงรุก
- **เพิ่มคนใหม่ในกลุ่มเปราะบาง** (เช่น ผู้สูงอายุที่เพิ่งติดเตียง) — ยังต้องผ่านแบบสอบถาม
